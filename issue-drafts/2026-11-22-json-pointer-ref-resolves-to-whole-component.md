# `$ref` with a JSON pointer into a component is generated as the whole component

## Summary

A `$ref` whose JSON pointer goes deeper than `#/components/<kind>/<name>` (for example
`#/components/schemas/Block/properties/fee` or `#/components/schemas/Block/properties/tags/items`) is
generated as a reference to the **whole** component (`z.lazy(() => BlockSchema)`) instead of the
referenced sub-schema.

The output compiles, so neither `tsc` nor a smoke test flags it. The generated validation schema is
simply wrong.

## Reproduction

`openapi.yaml`:

```yaml
openapi: 3.1.0
info:
  title: deep-pointer-repro
  version: 1.0.0
paths:
  /a:
    get:
      responses:
        '200':
          description: ok
          content:
            application/json:
              schema:
                type: object
                properties:
                  fee:
                    $ref: '#/components/schemas/Block/properties/fee'
                  tag:
                    $ref: '#/components/schemas/Block/properties/tags/items'
                  base:
                    $ref: '#/components/schemas/Derived/allOf/0'
components:
  schemas:
    Block:
      type: object
      properties:
        fee:
          type: string
          pattern: '^[0-9]+$'
        tags:
          type: array
          items:
            type: string
            pattern: '^[a-z]+$'
    Derived:
      allOf:
        - type: object
          properties:
            id:
              type: string
        - type: object
          properties:
            extra:
              type: string
```

```bash
npx hono-takibi@0.32.6 openapi.yaml -o routes.ts
```

## Expected

- `fee` is `z.string().regex(/^[0-9]+$/)`
- `tag` is `z.string().regex(/^[a-z]+$/)`
- `base` is the first `allOf` member of `Derived`

## Actual

```ts
.object({
  fee: z.lazy(() => BlockSchema).exactOptional(),
  tag: z.lazy(() => BlockSchema).exactOptional(),
  base: z
    .object({ id: z.string().exactOptional() })
    .exactOptional()
    .openapi({ required: [] }),
})
```

`fee` and `tag` become the `Block` object. `base` (a pointer ending in `allOf/0`) is resolved correctly,
so pointer resolution looks inconsistent rather than missing altogether.

## Where this comes from in real documents

Documents split across several files produce these pointers. When the same external fragment is used
more than once, `@apidevtools/swagger-parser`'s `bundle()` keeps the first occurrence inline and rewrites
the other uses as pointers into it, for example `#/components/schemas/Block/properties/fee`.

Ethereum's Beacon API is one such document. `beacon-node-oapi.yaml` pulls in 168 files and, after
bundling, has 61 distinct `$ref` targets that point deeper than a component root.

## Possibly related, not reduced

The generated `routes.ts` for the Beacon API also has names that are used but never declared. With
hono-takibi 0.32.6 and `@apidevtools/json-schema-ref-parser` 16.0.8 that is 18 `tsc` errors for 5 names
(`ItemsSchema` x12, `_0Schema` x2, `Attestation_1Schema` x2, `ExecutionPayloadSchema`,
`ExecutionBranchSchema`), plus one TS2375 on a recursive schema. They look like the last segment of a
pointer, which suggests the same area of code. I could not reproduce them with a smaller document, so this
issue is only about the case above.
